## Problem Statement

This is an entry for **Graph Hacks: Context for AI Agents** (WeMakeDevs x FalkorDB), running Oct 15 12:01 AM IST to Oct 18 11:59 PM IST 2026. I'm entering solo, against about 1,800 registrants. The brief is an agent whose decisions come out of a FalkorDB graph and can be traced back to it. Rule 3 sets the bar: if the product still works with FalkorDB removed, it doesn't qualify.

The problem: a vulnerable or malicious npm package lands, and an org running several services has to answer four questions quickly:

1. Which services are exposed, and through which dependency chains?
2. Where do those chains converge? Which packages does every exposed path in a service pass through, so that changing them removes the exposure?
3. Who owns each affected service and needs to know?
4. What did we decide about this last time, and does that decision still hold for today's dependency graph?

`npm audit`, Dependabot and Snyk each work one repo at a time. They list findings and suggest a fix version, and they do record ignore and dismissal reasons. What none of them does is the cross-service structural view: the exact convergence points across 5 services, who to notify across teams, and **past decisions checked again against the path that exists right now**. All of that is graph work.

## What Makes This Cool

- **Exact chokepoints, not heuristics.** For each exposed service, the agent computes the **minimum vertex cut** between the service and the vulnerable package: the smallest set of packages that every exposed path goes through. FalkorDB's `algo.maxFlow` runs on a node-split flow graph and computes the flow. Python reads the cut from the leftover-capacity graph and checks it with `cut size == maxFlow`. Output reads like: "svc-billing has 14 paths to `request`, and all of them go through 2 packages: `node-gyp@8` and `jsdom@16`."
- **It replays a real incident with no upstream fix.** The demo vulnerability has **no patched version**. The lead candidate is `request` CVE-2023-28155 (SSRF; `request` is deprecated and was never patched). That rules out the trivial answer of "override to the fixed version," which makes convergence points matter. The agent still names the drop-in mitigation when one exists (for `request`, an alias to the maintained fork `@cypress/request`) as **option 1**. It then shows the structural plan (chokepoints, and whether each one has a clean upgrade) for orgs that ban aliases and overrides, or where the fork doesn't fit.
- **Decision memory checked against today's graph.** A triage decision is stored as a graph node, together with the exact ordered path it assumed. In the next session the agent recalls it and re-checks it: "Last session you accepted `request` exposure in svc-docs because it's dev-only. It is still dev-only, so the decision holds. But svc-api has 1 new prod path through `x@2` that nobody has reviewed."
- **Per-visitor tenant graphs.** Every visitor to the live demo gets their own copy of the demo graph through FalkorDB's multigraph support (`GRAPH.COPY`). Their decisions never leak into anyone else's session. This is a real Track 02 point.

### Graph model (v0; /plan-eng-review finalises it)

One FalkorDB graph per tenant:

- `tmpl_replay`: the read-only template
- `v_<visitorId>`: a per-visitor copy made with `GRAPH.COPY`, expiring after 24h
- `flow_<runId>`: a scratch graph for each cut computation, dropped in `finally`, with a sweep every 15 min

```
(:Team {name})-[:OWNS]->(:Service {name, repo, commit, lockfile_version, max_depth})
(:Person {handle, synthetic:true})-[:MEMBER_OF]->(:Team)
(:Service)-[:DEPENDS_ON {scope:'prod'|'dev', optional:bool}]->(:PackageVersion)        // direct deps
(:PackageVersion {key:'name@version', name, version})-[:DEPENDS_ON {svcs:[...], scope, optional}]->(:PackageVersion)
(:PackageVersion)-[:VERSION_OF]->(:Package {name, deprecated:bool})
(:Vuln {id, aliases[], summary, severity, published, has_fix:bool, fixed_versions[]})-[:AFFECTS]->(:PackageVersion)
(:Package)-[:DROP_IN {source}]->(:Package)        // known safe forks, e.g. request -> @cypress/request
(:Decision {id, disposition:'accept'|'fix'|'defer', rationale, at, by, path_keys:[ordered], path_hash})-[:ABOUT]->(:Vuln)
(:Decision)-[:FOR]->(:Service)
(:Decision)-[:SUPERSEDES]->(:Decision)
(:Session {id, at})-[:RECORDED]->(:Decision)
```

- `PackageVersion` nodes are shared across services. Each transitive edge carries `svcs`, the list of services whose lockfile contains that edge. **Every per-service query filters on `$svc IN r.svcs`**, so a path cannot jump from one service's tree into another's.
- `path_hash = sha1("|".join(path_keys))`, where `path_keys` is the ordered list of `name@version` from the service to the vulnerable version.

### Loader contract (day 1)

- **Input:** `package-lock.json` with **`lockfileVersion >= 2`**. This is a selection criterion for the 5 repos. v1 and yarn are out of scope.
- **Edges:** build `DEPENDS_ON` edges from the `packages` map, keyed by `node_modules/...` path. For each entry, every name in `dependencies`, `optionalDependencies` and `peerDependencies` is resolved the way Node does it: look in `<path>/node_modules/<name>`, then walk up through ancestor `node_modules` directories to the root. If nothing resolves, log it and count it as `unresolved` in the load report. An unresolved optional or peer dependency is fine; an unresolved regular dependency fails that service's load.
- **Bundled dependencies** count as normal children.
- **Scope:** an entry with `dev:true` gets scope `dev`, otherwise `prod`.
- **`max_depth`:** measured per service with a BFS at load time.

### Traversal policy (applies to every query)

- **Prod scope only by default.** A `include_dev` toggle exists, and every evidence block shows which scope was used.
- **Depth cap:** `$maxDepth = max(Service.max_depth) + 2`, measured at load time. The loader fails if any service is deeper than 40.
- **No full path enumeration.** Queries extract the **node set reachable from the service that also reaches the vulnerable version**. Path counts come from a DAG dynamic-programming pass in Python; if a cycle is detected, the count falls back to "≥ N". Displayed paths are capped to the **shortest path per (service, direct parent)**, with the total count shown next to them.

### Hero queries (these go into the README)

1. **Exposure subgraph.** Find the services and the nodes on any path from service S to the vulnerable version:
   ```
   MATCH (s:Service)-[:DEPENDS_ON]->(d:PackageVersion)
   MATCH (d)-[:DEPENDS_ON*0..$maxDepth]->(pv)<-[:AFFECTS]-(v:Vuln {id:$id})
   ```
   Each hop is filtered with `$svc IN r.svcs` and on scope. Results are deduplicated per service and direct parent, and the shortest path for each is returned.
2. **Minimum vertex cut (chokepoints), per service.**
   - Copy the exposure subgraph into `flow_<runId>`. Each package node X is split into `(:N_in)-[:F {cap:1}]->(:N_out)`; every original edge becomes `N_out -[:F {cap:1000000}]-> M_in`.
   - Uncuttable: the service node, and the vulnerable `PackageVersion`, whose split edge gets cap 10^6.
   - A **direct dependency on the vulnerable package** is a cuttable unit with cost 1 ("remove or replace the direct use"). It is modelled as its own split node `DirectUse_in → DirectUse_out` between the service and the vulnerable version.
   - Run:
     ```
     CALL algo.maxFlow({sourceNodes:[svc], targetNodes:[vuln_in], relationshipTypes:['F'], capacityProperty:'cap'}) YIELD edges, edgeFlows, maxFlow
     ```
   - In Python, build the **residual graph**: forward arcs where `cap - flow > 0`, plus a **reverse arc for every edge with positive flow**. BFS from the source. The cut is the set of split edges going from a reachable node to an unreachable one. **Assert that the cut's total capacity equals `maxFlow`.** If it doesn't, raise an error and show it in the UI. Never present a wrong cut.
   - **No feasible cut:** if `maxFlow >= 10^6`, report "no cut possible" for that service. Show the paths and offer a drop-in alias or override if a `DROP_IN` edge exists, or else record an accept/defer decision.
3. **Org chokepoint summary.** Group the per-service cuts by package name, e.g. "`node-gyp` appears in the cut for 3 of 4 exposed services." This is aggregation only, labelled as such, with no claim of an org-wide optimum. (A grouped-cost optimum is a set-cover problem, which is NP-hard, and is out of scope.)
4. **Upgrade check for each cut node (1 hop).** Fetch `registry.npmjs.org/<name>/latest` and check whether its `dependencies` still lists the vulnerable package or the next node on the path. The result is labelled "clean at 1 hop" or "still depends." The live result is cached into the graph as `Package.latest_check`. **It is labelled as a 1-hop check, not a guarantee.** The oracle in the Success Criteria covers the full check for the demo incident.
5. **Notify.**
   ```
   MATCH (t:Team)-[:OWNS]->(s:Service)<-[:FOR]-... ; (p:Person)-[:MEMBER_OF]->(t)
   ```
   It runs over the services exposed in query 1, using the same scope and depth policy.
6. **Decision re-validation.** For each `Decision` on the vulnerability and service, re-run query 1 for that service and compare:
   - **HOLDS:** the decision's ordered `path_keys` still exist, and there are no new prod paths.
   - **STALE:** the decided path no longer exists (for example a version changed). The agent says "the path you decided on is gone. Re-triage?"
   - **NEEDS_REVIEW:** the decided path still exists, but **new paths** appeared for the same vulnerability and service. The agent lists only the new ones.
   - **SUPERSEDED:** a newer `Decision` points to this one through `SUPERSEDES`.

Stretch: `algo.betweenness` over the dependency subgraph, presented accurately as "**structural hubs**: packages that sit on many shortest dependency routes across the org." This is a separate panel. It is not a chokepoint and isn't claimed to be one.

## Reviewer Concerns

Disposition: CONCERNS_RECORDED

Stop: CONVERGENCE

### R2-1 — feasibility

**Problem**

> Within a single service, PackageVersion nodes are keyed by name@version. A v2/v3 lockfile can install the same name@version at several node_modules paths, and each copy can resolve its children to different versions through the Node walk-up the loader contract itself specifies. Merging those copies into one node unions their child edges. That creates paths that do not exist in the real tree (for example A -> X@1 -> Y@2 -> vuln when only B's copy of X resolves Y@2). The svcs filter stops leaks between services but not leaks between copies inside one service. The result inflates exposure, direct-parent sets and path counts, can distort the cut, and will disagree with the npm ls oracle.

**Remedy**

> Either key the flow and exposure graph per install path (node_modules path) within a service and map cut nodes back to name@version for display, or have the loader detect copies of the same name@version whose resolved children differ and fail or flag that service. Document the choice.

### R2-2 — feasibility

**Problem**

> Transitive DEPENDS_ON edges are shared across services (svcs:[...]) but carry a single scope and a single optional value. The same edge X@1 -> Y@1 can be prod in one service and dev in another, so the 'prod scope only by default' filter returns wrong results for at least one service. The loader also derives scope from the child entry's dev flag, which is a per-lockfile fact, not a per-edge one.

**Remedy**

> Make scope (and optional) per service, for example prod_svcs and dev_svcs lists on each edge, or separate edges per service, and filter on $svc IN r.prod_svcs in the traversal policy.

### R2-3 — feasibility

**Problem**

> The depth cap ($maxDepth = max(Service.max_depth) + 2) comes from a BFS, which measures shortest distance from the service. The longest simple path, and the hop count from a particular direct parent to the vulnerable version, can be much longer than the deepest BFS distance. The cap can therefore drop real paths and nodes, which is the 'misses a transitive path' failure Premise 6 calls credibility-ending.

**Remedy**

> Measure the longest path length per service at load time (DAG dynamic programming, with a cycle fallback), or extract the reachable node set without a hop bound (forward reachability from the service intersected with backward reachability from the vulnerable version). Justify the cap from that measurement.

### R2-4 — feasibility

**Problem**

> Hero query 1 says 'each hop is filtered with $svc IN r.svcs and on scope' and also that there is no full path enumeration. In Cypher, a per-hop predicate on a list property over a variable-length pattern normally needs a path variable with all(r IN relationships(p) WHERE ...), which enumerates paths, the explosion the traversal policy rules out. The document never says how per-service node-set extraction is actually executed in FalkorDB.

**Remedy**

> Specify the mechanism and confirm it in the pre-Oct-15 scratch Docker check. Options: per-service edge types or properties that FalkorDB can filter inline, a per-service projected subgraph, or iterative frontier BFS (one hop per query) driven from Python.

### R2-5 — feasibility

**Problem**

> Hero query 1 writes the hop bound as a parameter (DEPENDS_ON*0..$maxDepth). Cypher engines generally do not accept parameters in variable-length bounds, and FalkorDB support for this is not established, so the README query as written may not run.

**Remedy**

> Confirm FalkorDB's behavior in the scratch instance. If parameters are unsupported, state that the bound is interpolated into the query string as a validated integer, and show that form in the README.

### R2-6 — feasibility

**Problem**

> The correctness oracle requires our path counts to match npm ls <pkg> --all. npm ls prints a tree of install locations and marks repeated subtrees as 'deduped' without expanding them. Its output is not a count of distinct dependency paths, so the comparison as specified is undefined or will fail even when the graph is correct.

**Remedy**

> Define exactly what is compared against npm ls, for example the set of exposed services, the set of direct parents and the set of vulnerable install locations parsed from npm ls --json. Either validate path counts another way or drop path counts from the oracle.

### R2-7 — consistency

**Problem**

> The structural plan is pitched at 'orgs that ban aliases and overrides', yet most chokepoints will be transitive packages (the example node-gyp@8, jsdom@16). A transitive package can only be changed by an override (banned for that audience) or by bumping its ancestors until a release whose range excludes it. The 1-hop check only looks at the chokepoint's own latest release and explicitly skips semver ranges, so a 'clean at 1 hop' result does not tell that audience any action they are allowed to take.

**Remedy**

> State what action a transitive chokepoint implies for an org that bans overrides (for example, the direct parent to bump and whether its newer release drops the chokepoint version), or reframe the chokepoints as an exposure-structure insight rather than a remediation plan, and keep the demo narration consistent with that.

### R2-8 — consistency

**Problem**

> The Synthesis argues the cut 'only means something when ... the vulnerable package has no trivial fix', and that is the stated reason for choosing a no-fix incident. The lead incident does have a one-line fix: alias request to @cypress/request. It is shown first as option 1 (auto-decision 6, Open Question 5). By the document's own reasoning, the hero chokepoints become secondary in the lead demo, and the only remaining motivation, an alias or override ban, is an assumption with no evidence behind it.

**Remedy**

> Reconcile the rationale with the incident choice. Either pick an incident with no drop-in alias, or state explicitly that the chokepoints matter because of an alias/override-ban policy and narrate that policy in the demo. Revise the Synthesis sentence either way.

### R2-9 — clarity

**Problem**

> The Problem Statement (Q2: 'Which packages does every exposed path in a service pass through') and the example output ('all of them go through 2 packages: node-gyp@8 and jsdom@16') describe dominators: packages that are on every path. A minimum vertex cut is a set where every path passes through at least one member. These are different results, and judges who know graphs will spot it.

**Remedy**

> Reword Q2 and the example as 'every exposed path passes through at least one of these packages', or compute and present dominators separately if that is the intended claim.

### R2-10 — clarity

**Problem**

> Minimum vertex cuts are often not unique. The residual BFS from the source returns one particular minimum cut, the one closest to the source. Hero query 3's org summary ('node-gyp appears in the cut for 3 of 4 exposed services') depends on that tie-breaking, so it can understate packages that appear in equally valid alternative cuts. The document does not say which cut is returned.

**Remedy**

> State that the reported cut is the source-closest minimum cut, label the org summary accordingly, and optionally report when an alternative minimum cut exists (for example by also computing the sink-closest cut).

### R2-11 — clarity

**Problem**

> Persisting from R1-18. NEEDS_REVIEW fires when 'new paths appeared', but a Decision stores a single ordered path_keys, and the design forbids full path enumeration. Nothing records which paths or direct parents existed and were reviewed when the decision was made. Any service with more than one exposed path would therefore always count as having 'new' paths, so the rule cannot be evaluated.

**Remedy**

> Store a reviewed baseline on the Decision, for example the set of (direct parent, vulnerable version) pairs or the node-set hash at decision time. Define 'new' as baseline elements that are now present but were absent then, computed with the same node-set extraction.

### R2-12 — consistency

**Problem**

> The flagship recall example accepts svc-docs exposure 'because it's dev-only' and later reports HOLDS. Re-validation re-runs query 1, which is prod-only by default under the traversal policy. A dev-only decided path would not be found, so the rule as written yields STALE, contradicting the example.

**Remedy**

> Specify that re-validation runs query 1 in the scope recorded on the Decision (store scope on the Decision), or with include_dev on, and update the HOLDS rule to match.

### R2-13 — completeness

**Problem**

> HOLDS only checks that path_keys still exist and that there are no new prod paths. It does not re-check the premise behind the decision. If the accepted dev-only path became prod (the same name@version keys, but the scope changed), the decision would still report HOLDS, even though its rationale ('dev-only') is now false.

**Remedy**

> Record the scope (and any other fact the decision relies on) on the Decision. Have re-validation return STALE or NEEDS_REVIEW when that fact has changed, with a message naming the change.

### R2-14 — clarity

**Problem**

> The four re-validation states are not mutually exclusive. A decision can be superseded and also have its path gone, or its path can be gone while new paths appear. No precedence is defined, so the badge shown in the UI and checked by the success criterion is ambiguous.

**Remedy**

> Define a precedence order (for example SUPERSEDED > STALE > NEEDS_REVIEW > HOLDS) or allow multiple badges, and state which one the success criterion checks.

### R2-15 — consistency

**Problem**

> Canned demo questions are 'served from cached transcripts'. Those answers would keep working with FalkorDB removed, contradicting the success criterion 'Removing FalkorDB breaks every feature' (rule 3). They would also ignore the visitor's own v_<visitorId> graph, for example a visitor's recorded decision would not appear in a cached recall answer, contradicting 'coming only from the graph'.

**Remedy**

> Cache only the LLM narration while re-executing every tool query live against the visitor's graph, or label cached answers on screen as recorded replays, exclude them from the rule-3 claim, and never use them for recall or decision questions.

### R2-16 — clarity

**Problem**

> The 'under 30 seconds for canned prompts' success criterion is met trivially if canned prompts are served from cached transcripts, so it does not measure the system.

**Remedy**

> State that the latency criteria are measured on uncached end-to-end runs (agent plus live queries) against the replay tenant.

### R2-17 — completeness

**Problem**

> @falkordb/mcpserver connects as a single read-only ACL user and the LLM chooses which graph to query. Nothing stops an ad-hoc question from reading another visitor's v_<visitorId> graph, so decisions can leak between sessions. That contradicts 'Their decisions never leak into anyone else's session.'

**Remedy**

> Scope ad-hoc access to the current visitor's graph: per-request key-pattern ACLs, a proxy that pins the graph name, or exposing only tmpl_replay to mcpserver. State which one is used.

### R2-18 — feasibility

**Problem**

> Read-only enforcement depends on an ACL user that can run only GRAPH.RO_QUERY. If @falkordb/mcpserver issues GRAPH.QUERY (or other commands such as GRAPH.LIST) for reads, every ad-hoc query will be rejected and the feature breaks. Whether it does is not verified, and it is not in the pre-Oct-15 checks. FalkorDB Cloud ACL support is also unconfirmed.

**Remedy**

> Add to Next Step 1: confirm which commands mcpserver sends and that a GRAPH.RO_QUERY-only ACL user works on FalkorDB Cloud. Document a fallback, such as a read-only mode in mcpserver or a thin proxy that rewrites to RO_QUERY.

### R2-19 — completeness

**Problem**

> Each new visitor gets a GRAPH.COPY of the template, but there is no authentication and no cap on how many visitor graphs can be created. A script that rotates visitor IDs can create unlimited copies and exhaust FalkorDB Cloud memory, taking the live demo down during judging.

**Remedy**

> Cap the number of live visitor graphs and their creation rate (globally and per IP). When the cap is reached, fall back to read-only access on the template or to evicting the oldest graph.

### R2-20 — completeness

**Problem**

> Visitor graphs 'expire after 24h', but no mechanism is given. The sweep is described only for flow_* graphs, and nothing says whether a Redis key TTL or a sweep enforces the visitor expiry.

**Remedy**

> Specify the expiry mechanism for v_* graphs (key TTL refreshed on access, or a sweep based on a last-used timestamp) and where that timestamp is stored.

### R2-21 — clarity

**Problem**

> Hero query 5 (notify) is a placeholder, not a query: 'MATCH (t:Team)-[:OWNS]->(s:Service)<-[:FOR]-... ; (p:Person)-[:MEMBER_OF]->(t)'. The FOR relationship links Decisions, not exposure, and the README must list the Cypher the product depends on.

**Remedy**

> Write the actual notify query (exposed services from query 1 -> owning Team -> member Persons) with its scope and depth filters.

### R2-22 — clarity

**Problem**

> The blast_radius tool ('reverse reachability from a package') has no query, no scope or svcs filtering rule, no output definition and no demo role, unlike the other six tools, which map to hero queries.

**Remedy**

> Define blast_radius's query, its filters and its output, or drop it and adjust the tool count.

### R2-23 — clarity

**Problem**

> The Success Criteria say expected oracle outputs are 'saved in notes/oracle/ before Oct 15'. The cut oracle, however, applies the product's planned cut, which does not exist before Oct 15 under rule 8, so the cut part cannot have a saved expected answer.

**Remedy**

> Separate the two: exposure expected answers are saved before Oct 15, and the cut oracle is a CI procedure that runs on the computed cut (or on a hand-derived expected cut, if one is prepared before Oct 15).

### R2-24 — consistency

**Problem**

> The Assignment differs from Next Step 2. It omits the lockfileVersion >= 2 check and the osv-scanner output. 'Clone 5 candidate apps ... keep the 5 where at least 3 show exposure' also leaves unclear how many candidates to screen and what happens if the criterion is not met (switch to a fallback incident?).

**Remedy**

> Align the Assignment with Next Step 2 (lockfile version check, osv-scanner output) and state the candidate pool size and the fallback if fewer than 3 repos qualify.

### R2-25 — completeness

**Problem**

> The loader contract does not handle workspace or link entries (link:true, packages resolved to a local folder) in v2/v3 lockfiles. These are common in real npm apps, and under the stated rule they would make regular dependencies unresolved and fail the service's load.

**Remedy**

> Either add 'no workspaces' as a repo-selection criterion or specify how link entries are followed to their target package entry.

### Prior finding evidence

**R1-14 → R2-3 (persisting)**

> One depth policy is now applied everywhere, but it is justified from a BFS max_depth (shortest distance), not the actual maximum path depth in the lockfiles, so the cap can still miss paths.

**R1-18 → R2-11 (persisting)**

> HOLDS/STALE/NEEDS_REVIEW/SUPERSEDED are now defined, but NEEDS_REVIEW depends on 'new paths' with no stored baseline of reviewed paths (the Decision keeps a single path_keys), so the rule for new unreviewed paths still cannot be evaluated.
