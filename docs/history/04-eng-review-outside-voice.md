## Findings the review missed

**1. `algo.bfs` direction and `edges` semantics are correctness-critical but unlisted as unverified.** Part B's own fact table says BFS "has no direction parameter." If BFS is undirected, the subgraph includes nodes the attacker can't reach, and projecting those edges forward invents routes to jewels — the cut cost becomes wrong, not just large. Worse: if `YIELD edges` returns only BFS **tree** edges (one parent per node), the projection *loses alternate routes* and the min cut comes out **too cheap** — a silently wrong hero number that the `cut == maxFlow` assertion cannot catch (it only validates the residual BFS). This belongs in T4 above `GRAPH.COPY`. Fallback: build the subgraph with a Cypher variable-length match or iterative frontier expansion, directed.

**2. The min cut is not unique; the demo names specific grants.** Residual-BFS yields the source-minimal cut *for the flow FalkorDB happened to return*. A different maximum flow of equal value gives a different min cut. `expected.yaml`, beat 3's owners/tickets, and beat 5's "3 grants, cost 5" are therefore not reproducible — only the *cost* is. Fix: make the min cut unique by tie-breaking capacities (`cap = cost*N + rank(grant_id)`, then report the integer costs), or assert cost only and never assert grant identity.

**3. `routes` is bounded by the number of entry edges.** Setting *every* projected edge to capacity 1 caps flow at the Finding's out-degree — so "19 attack paths" becomes 2–3. Fix: entry/structural edges keep cap ∞ in the routes run, grants get 1. Also `nx.edge_disjoint_paths` is single-sink; the oracle test needs a super-sink, which isn't stated.

**4. Beat 7 probably no-ops.** Part A beat 2 says `billing-secrets` is already reachable from F-1. If it's in `baseline_jewels`, granting `deployer` READS on `billing-secrets` leaves the set unchanged → **HOLDS**, not NEEDS_REVIEW. The event must introduce a jewel that was *not* in the baseline. Related: "strict superset" misses non-monotone drift (set changes without growing) — use set-difference with added/removed listed. And "jewels reachable from the grant's target" is not "reachable *via* the grant," so it will fire on changes the grant has nothing to do with.

**5. Lifecycle races.** No lease/refcount: LRU eviction can delete a graph mid-SSE-run. Create-then-register leaves a window where the reconciler deletes a live visitor graph or another worker's `flow_*`; register-before-create isn't specified. Multiple uvicorn workers → concurrent sweepers. Old `tmpl_<sha>` graphs are never deleted, and the seed runs on *every deploy* — unbounded graph growth against the same instance as the 150-graph cap. 150 × 5k nodes has no memory budget anywhere; 150 is unjustified.

**6. Noise isolation may not converge.** The rule forbids *any* noise grant creating an entry→jewel route, and the retry unit is the whole sub-seed. With 150 people and dense random grants, most seeds violate it; fix by rejecting individual candidate edges, not reseeding.

For one builder in four days, with deploy frozen 18:00 Day 4 and a video, this is roughly double what fits. **There is no day-by-day plan, no ordering, and no cut line** — the single largest gap in an "implementation-ready" review. Highest-value cuts, in order: per-visitor tenancy (judges score graph work, not multi-tenancy — one shared read-only graph + decisions namespaced by visitor id removes ENG-6 entirely), the sweeper/eviction, Cytoscape (static SVG), `ask_graph`.
